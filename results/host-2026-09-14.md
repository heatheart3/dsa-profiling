# DSA copy-to-iter-like benchmark — 2026-09-14

## Host and configuration

- CPU: Intel Xeon 6980P, 1 socket, 128 cores / 256 logical CPUs
- Kernel: Linux 7.0.0-30-generic
- IOMMU: `intel_iommu=on,sm_on`
- Device: `dsa0`, NUMA node 0, PASID enabled
- Group 0: `engine0.0` through `engine0.3`
- Work queue: `wq0.0`, dedicated user WQ, size 32
- Operation: DSA MEMMOVE (`opcode 3`), 64 KiB per descriptor
- Source and destination start in memory (`-zF,F`)
- Destination cache-control enabled (`-f`), so copied data is allocated in cache
- Submitter: CPU 0; descriptors use varying portal cache lines (`-c`)

The reported bandwidth counts useful copied bytes once. A copy also causes source
reads and destination writes, so it is not the sum of memory-bus read and write
traffic.

## Queue-depth sweep

| QD | GB/s | 64 KiB operations/s | Notes |
|---:|-----:|---------------------:|-------|
| 1  | 19.583 | 298k | 3.347 us completion latency |
| 2  | 33.050 | 504k | |
| 4  | 51.570 | 786k | exceeds the 50 GB/s target |
| 8  | 59.533 | 908k | saturated |
| 16 | 59.473 | 907k | saturated |
| 32 | 59.329 | 905k | saturated |

Five longer QD32 runs produced 59.492, 59.558, 59.528, 59.477 and
59.501 GB/s: mean **59.511 GB/s**, range **0.081 GB/s**.

Removing the destination cache-control flag reduced QD32 bandwidth to
**44.999 GB/s**.

The real single-threaded hot-page-cache `pread()` baseline (64 KiB reads from a
512 MiB populated memfd) measured **8.44–10.64 GB/s**, or **6.16–7.77 us/read**.
It includes syscall and `copy_page_to_iter()` overhead but excludes storage I/O.
Its wider variation is consistent with CPU 0 running under the `powersave`
governor; unlike the DSA result, this path keeps the CPU busy copying data.

## Interpretation

The best repeatable DSA data-path result is about **59.5 GB/s**. Four engines are
already saturated at about QD8; QD32 adds enough outstanding work but does not
increase the engine limit.

A conventional synchronous `read()` cannot expose QD32 by itself: it must finish
the copy before returning. One read at a time therefore behaves like QD1 and is
bounded here at about **19.6 GB/s**, before adding syscall, iterator construction,
page pin/fault handling, and completion-wakeup overhead. Reaching 50 GB/s needs at
least four concurrent/in-flight 64 KiB copies on this host. That can come from
multiple readers or an explicitly asynchronous kernel implementation.

The measured CPU `pread()` result is lower still (8.44–10.64 GB/s), as expected:
the syscall does real CPU copying and pays the filemap/iterator path on every
64 KiB request. It is a semantic baseline, not a claim that replacing
`copy_to_iter()` with a synchronous DSA submission will automatically improve
latency; at 64 KiB, submission, translation, and completion waits remain material.

This benchmark uses a user WQ and SVA addresses. It reproduces the 64 KiB memory
movement, cache state, engines, and queueing behavior, but it does not execute the
kernel's `copy_to_iter()` function or include syscall overhead. A true kernel
prototype needs a kernel WQ and must pin/map every userspace page (or provide an
equivalent fault-capable SVA path) before DSA can safely write it.

## If a run is below 50 GB/s

Check these causes in order:

1. QD below 4, or synchronous completion after every descriptor.
2. Destination cache-control disabled (45.0 GB/s here).
3. Fewer than four engines assigned to the WQ's group.
4. WQ size/credit limit below the requested QD, or shared-WQ ENQCMD retries.
5. Submitter and memory on a remote NUMA node.
6. Page faults or IOMMU/device-TLB misses in the timed loop; pre-fault buffers.
7. CPU power governor, interrupt preemption, or a busy submitter core. The test
   host was in `powersave`, and the helper utilities were absent, although the DSA
   result remained stable.
8. Competing traffic in the DSA group, LLC, IOMMU, or memory controllers.
9. Verification, buffer initialization, cache flushing, or syscall work included
   in the timed interval when comparing against the pure data-path number.
